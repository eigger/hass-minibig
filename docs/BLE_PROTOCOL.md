# MiniBig BLE Protocol Specification

This document specifies the Bluetooth Low Energy (BLE) communication protocol for MiniBig smart home devices.

---

## 1. Overview & GATT Architecture

MiniBig devices communicate via standard Bluetooth Low Energy (BLE) GATT characteristics. Devices operate locally without requiring cloud authentication or pre-shared session keys.

### 1.1 GATT Services and Characteristics

| Target | Service UUID | Write Characteristic (W) | Notify Characteristic (N) |
|---|---|---|---|
| **Standard Devices** (Window Opener, PushMini, SwitchMini) | `2b8d0001-6828-46af-98aa-557761b15400` | `2b8d0002-6828-46af-98aa-557761b15400` | `2b8d0003-6828-46af-98aa-557761b15400` |
| **HubMini Gateway** (External bridge) | `c7d71110-5878-4934-9db6-f1d1cc845b2c` | `c7d71111-5878-4934-9db6-f1d1cc845b2c` | `c7d71112-5878-4934-9db6-f1d1cc845b2c` |

## 2. BLE Advertisement & Discovery

Device identification is performed by matching the 128-bit `DEVICE_SERVICE_UUID` (`2b8d0001-6828-46af-98aa-557761b15400`).

### 2.1 Manufacturer Specific Data Layout (AD Type 0xFF)

The raw manufacturer data payload (including the 2-byte company ID in little-endian format) is structured as follows:

```
Offset (bytes)   Field        Description
0..1             Company ID   Manufacturer identifier (little-endian)
2                Flags Byte:
                   bit 0      init_mode (True = device in pairing/setup mode)
                   bit 1..5   fv (Firmware version, 0..31)
                   bit 6..7   rev (Hardware revision, 0..3)
3..8             Reserved     Device-specific runtime state
9..10            IDV          2-byte device identifier (hex string, e.g. "1CFE", "AFEA")
11..12           Reserved     Internal status
13               d_type       Device type (1 = PushMini series, 2 = HubMini, etc.)
```

### 2.2 Advertisement Parsing Rules

1. **IDV Extraction**:
   - When payload length $\ge 12$, `IDV = hex(manu[9..10]).upper()`.
   - When payload length $< 12$, `IDV = "0000"`.
2. **Device Classification**:
   - If local name contains `clpm` (case-insensitive), `d_type = 1` (PushMini).
   - If `d_type == 1`, the device is a **Legacy PushMini** if:
     $$\text{rev} = 0 \lor (\text{rev} = 1 \land \text{fv} \le 9) \lor (\text{rev} = 2 \land \text{fv} \le 5) \lor (\text{rev} = 3 \land \text{fv} \le 5)$$
     Otherwise, it is a **Modern PushMini** (using DP triplets).
   - If `d_type == 2`, the device is a **HubMini** (unsupported in direct BLE).

## 3. Command Frame Format

All command frames sent to the Write Characteristic (`2b8d0002-...`) follow this structure:

```
+----------+--------------------+--------------------+
|  Byte 0  |     Byte 1..2      |      Byte 3..      |
+----------+--------------------+--------------------+
|  Method  |   IDV ^ PASS_KEY   |   Method Payload   |
| (Opcode) | (Encrypted Header) |   (Data Points)    |
+----------+--------------------+--------------------+
```

### 3.1 Header Encryption Key (`PASS_KEY`)

The 2-byte header is generated by XOR-ing the 2-byte IDV with the static key `[0x66, 0x39]`:

$$\text{Header}[0] = \text{IDV}[0] \oplus 0\text{x}66$$
$$\text{Header}[1] = \text{IDV}[1] \oplus 0\text{x}39$$

#### Verified Golden Vectors:
- **Window Opener** (`IDV = "1CFE"` $\to [0\text{x}1\text{C}, 0\text{x}\text{FE}]$):
  - $0\text{x}1\text{C} \oplus 0\text{x}66 = 0\text{x}7\text{A}$
  - $0\text{x}\text{FE} \oplus 0\text{x}39 = 0\text{x}\text{C}7$
  - Open (100%): `2a 7a c7 00 00 64`
  - Stop (0%): `2a 7a c7 03 00 00`
- **PushMini** (`IDV = "AFEA"` $\to [0\text{x}\text{AF}, 0\text{x}\text{EA}]$):
  - $0\text{x}\text{AF} \oplus 0\text{x}66 = 0\text{x}\text{C}9$
  - $0\text{x}\text{EA} \oplus 0\text{x}39 = 0\text{x}\text{D}3$
  - Turn On: `2a c9 d3 00 00 01`

## 4. Opcodes and Data Models

### 4.1 Opcode Table

| Opcode (Dec) | Opcode (Hex) | Name | Description |
|---|---|---|---|
| `2` | `0x02` | `ACTION` | Legacy PushMini on/off action |
| `3` | `0x03` | `SETTING` | Legacy PushMini configuration setting |
| `4` | `0x04` | `READ_SETTING` | Legacy PushMini status query |
| `5` | `0x05` | `TIMER_SAVE` | Save schedule timer (Legacy) |
| `6` | `0x06` | `TIMER_READ` | Query active timers (Legacy) |
| `7` | `0x07` | `TIMER_DELETE` | Delete scheduled timer (Legacy) |
| `8` | `0x08` | `MANU_RESET` | Factory reset (Legacy) |
| `17` | `0x11` | `RESTART` | Device system reboot |
| `24` | `0x18` | `REPORT_DPS` | Live streaming status push from peripheral |
| `42` | `0x2A` | `PUB_DPS` | Publish / Write DP values (Modern) |
| `43` | `0x2B` | `READ_DPS` | Read all active DP values (Modern) |
| `44` | `0x2C` | `TIMER_SAVE_NEW` | Save schedule timer (Modern) |
| `45` | `0x2D` | `TIMER_READ_NEW` | Query active timers (Modern) |
| `46` | `0x2E` | `TIMER_DELETE_NEW` | Delete scheduled timer |
| `47` | `0x2F` | `MANU_RESET_NEW` | Factory reset (Modern) |

### 4.2 Modern DP (Data Point) Triplet Format

For opcode `42 (PUB_DPS)` and opcode `43 (READ_DPS)`, payloads are serialized as repeated 3-byte triplets:

```
+------------+--------------------+-------------------+
|   Byte 0   |       Byte 1       |      Byte 2       |
+------------+--------------------+-------------------+
|   dp_id    |   val_high (MSB)   |   val_low (LSB)   |
|  (1 byte)  |      (1 byte)      |     (1 byte)      |
+------------+--------------------+-------------------+
```

#### Standard DP Mapping — Verified on Real Hardware

Confirmed by capturing `43 (READ_DPS)` dumps on a CLWM-B06 window opener before and
after isolated open/close/stop operations (2026-08-19). These four DPs cover
everything the integration actively controls or reports.

| DP ID | Target Device | Name / Function | Value Range | Units |
|---|---|---|---|---|
| `0` | Window Opener | Target / Current Position | `0` ~ `100` | % — `0` = fully closed, confirmed exact. Fully open settled at `97` on the tested unit (matched the vendor app's own reading exactly), not `100`; the value is passed through unmodified rather than rounded to an assumed endpoint. |
| `0` | PushMini / Switch | Power / On-Off State | `0` or `1` | Boolean (0=Off, 1=On) |
| `3` | Window Opener | Stop Movement | `0` | Trigger. Sent to a stationary motor, it returns the current position without any physical movement — used for passive polling. |
| `10` | All Devices | Battery Level | `0` ~ `100` | % (read-only; drifts by a point or two between reads even at rest, treat as approximate) |

A full `READ_DPS` dump on that same unit returned DP IDs `0`–`19` (20 triplets, no
partial response). Beyond the four above, values on IDs `1,2,4–9,11,12,14–19` were
observed to shift only during the vendor app's initial setup wizard (mount type,
opening direction, travel-limit measurement) and stayed constant across ordinary
open/close/stop cycles afterward — consistent with one-time commissioning data, not
anything read or written during normal operation. Mapping those individually was
deliberately not pursued: they are set once at physical installation and have no
ongoing operational use. See §4.4 for the DP *codes* (not IDs) the vendor app uses
for this class of settings, if a future need arises. `minibig.send_raw` (method 43)
and `minibig.publish_dps` remain available for anyone who wants to identify them.

### 4.3 Legacy PushMini Bitfield Layout (`Opcode 3: SETTING`)

For legacy PushMini devices, configuration parameters are packed into bitfields:

$$\text{Byte 0} = (\text{rotate} \ll 7) \mid (\text{mode} \ll 6) \mid (\text{direction} \ll 5) \mid (\text{isOn} \ll 4) \mid (\text{mPower} \ll 2) \mid \text{delayTime}$$

$$\text{has\_back\_power} = (\text{rev} \ne 0) \land \neg(\text{rev} = 1 \land \text{fv} < 9) \land \neg(\text{rev} = 2 \land \text{fv} < 5) \land \neg(\text{rev} = 3 \land \text{fv} < 5)$$

- When `has_back_power` is `True`:
  - `Byte 0`'s `mPower` field is set to 0.
  - `Byte 1` is appended: $(\text{bPower} \ll 3) \mid \text{mPower}$.

### 4.4 Device Operation Data Points

Motor products (window, curtain and blind mountings of the same drive unit) expose
their operations as ordinary DPs published with opcode `42 (PUB_DPS)`. No dedicated
opcode is used for any of them.

| Operation | DP Code | Value |
|---|---|---|
| Drive open | `openMotor` | `true` |
| Drive closed | `closeMotor` | `true` |
| Halt | `stopMotor` | `true` |
| Open level | `openLevel` | `0`–`100` |
| Close level | `closeLevel` | `0`–`100` (`100` = fully closed, `0` = fully open) |
| Enter / leave measurement mode | `measureMode` | `true` / `false` |
| Jog during measurement | `measureEnable` | `true` / `false` |
| Store upper limit | `limit_set_del` | `limit_set_up` |
| Store lower limit | `limit_set_del` | `limit_set_down` |
| Clear upper limit | `limit_set_del` | `limit_del_up` |
| Clear lower limit | `limit_set_del` | `limit_del_down` |
| Reset stored position | `initLoc` | `true` |
| Reset motor direction | `control_back` | `forward` |
| Enter remote pairing mode | `pair_emitter` | `true` |
| Motor sensitivity | `motorSensitivity` | numeric |

A measurement run drives the motor with `openMotor` / `closeMotor` while
`measureMode` is active, and the operator stores each mechanical end with
`limit_set_up` / `limit_set_down`. Devices without stored limits report
`DEVICE_NOT_MEASURED` and refuse positional commands.

> **Value encoding.** DP values are transported as unsigned 16-bit integers, so
> booleans map to `1` / `0` directly. The limit and direction operations instead
> carry enumerated *string* values; the integer each enum maps to is provisioned per
> product alongside the DP ID and is not fixed by the protocol.

> **DP IDs.** The numeric DP IDs behind these codes are provisioned per product. A
> client must either be told the mapping or discover it by dumping `43 (READ_DPS)`
> and correlating the returned DP IDs.

Further motor settings cover mounting type (window / curtain / blind), curtain
arrangement (one-sided / split), opening direction, operating mode, travel length and
installation position.

### 4.5 Product Definition

DP IDs, schema types and enum orderings are not fixed by the protocol. They are
carried in a per-product definition that a client must obtain out of band. The parts
a BLE client needs are:

```
productBean
├─ mainProtocol            "ble" | "mqtt" | ...
├─ bleDataSet              { serviceUUID, writeUUID, notifUUID }
└─ dpsCodeMap              keyed by DP code
   └─ <code>
      ├─ id                numeric DP ID used on the wire
      ├─ schemaType        "bool" | "value" | "enum" | ...
      ├─ range             ordered label list for enum DPs
      │                    (the wire value is the index into this list)
      ├─ min / max / step / scale
      └─ unit
```

Resolution works in both directions: a code is mapped to `id` when building a
`42 (PUB_DPS)` payload, and an incoming DP ID is mapped back to its code and
`schemaType` when decoding a response (§5.3). A DP whose ID is absent from the map
cannot be encoded or interpreted.

### 4.6 Timer Payloads

**`44 (TIMER_SAVE_NEW)`** — a 7-byte timer record followed by a 4-byte local epoch:

```
Byte 0     activated (bit 7) | t_id (bits 0..6)
Byte 1     dp_id
Byte 2..3  value              (big-endian, unsigned 16-bit)
Byte 4..5  hour * 60 + minute (big-endian, unsigned 16-bit)
Byte 6     weekday mask, or 0xFF for a single-shot timer
Byte 7..10 local epoch        (big-endian, unsigned 32-bit)
```

Weekday mask bits: `Mon = 0x80`, `Tue = 0x40`, `Wed = 0x20`, `Thu = 0x10`,
`Fri = 0x08`, `Sat = 0x04`, `Sun = 0x02`. Bit 0 is unused.

**`45 (TIMER_READ_NEW)`** — a 4-byte local epoch only.
**`46 (TIMER_DELETE_NEW)`** — a single byte holding `t_id`.

The epoch is **local wall-clock time**, i.e. UTC epoch plus the client's UTC offset,
not UTC itself.

**Legacy equivalents.** `5 (TIMER_SAVE)` uses a 3-byte record plus the same time field:

```
Byte 0  value (bit 7) | activated (bit 6) | t_id (bits 3..5) | minutes >> 8 (bits 0..2)
Byte 1  minutes & 0xFF
Byte 2  weekday mask, or 0xFF for a single-shot timer
```

### 4.7 Legacy Opcode Substitution

Legacy PushMini firmware does not implement the DP-based opcodes. A client targeting
such a device substitutes them as follows:

| Modern | Legacy | Note |
|---|---|---|
| `42 PUB_DPS` | `2 ACTION` | When the DP is the on/off control |
| `42 PUB_DPS` | `3 SETTING` | For any other parameter |
| `43 READ_DPS` | `4 READ_SETTING` | |
| `44 TIMER_SAVE_NEW` | `5 TIMER_SAVE` | |
| `45 TIMER_READ_NEW` | `6 TIMER_READ` | |
| `46 TIMER_DELETE_NEW` | `7 TIMER_DELETE` | |
| `47 MANU_RESET_NEW` | `8 MANU_RESET` | |

## 5. Response Frame Format

Responses received via the Notify Characteristic (`2b8d0003-...`) follow this structure:

```
+----------+----------+------------------------------------+
|  Byte 0  |  Byte 1  |              Byte 2..              |
+----------+----------+------------------------------------+
|  Method  |  Status  |            Data Payload            |
| (Opcode) |  (Code)  | (DP Triplets or Method Body)       |
+----------+----------+------------------------------------+
```

### 5.1 Status Codes

| Status (Dec) | Status (Hex) | Name | Meaning |
|---|---|---|---|
| `102` | `0x66` | `DEVICE_UNAUTH` | Client is not authorised for this device |
| `238` | `0xEE` | `DEVICE_EXCEED_TIMER_NUM` | Timer storage capacity exceeded |
| `251` | `0xFB` | `DEVICE_SAME_DIRECTION` | Motor is already travelling in the requested direction |
| `252` | `0xFC` | `DEVICE_NOT_INITIAL` | Device is not initialised (e.g. travel limits not measured) |
| `253` | `0xFD` | `DEVICE_SUCCESS` | Command executed successfully |
| `254` | `0xFE` | `DEVICE_BUSY` | Peripheral is busy processing another action |
| `255` | `0xFF` | `DEVICE_NOT_MATCHING` | Header did not match the device (IDV mismatch) |

Any status other than `253` terminates the transaction; the value is the error code.
A frame shorter than 2 bytes is invalid.

### 5.2 Response Body by Opcode

The body begins at byte 2 in every case.

| Opcode | Body |
|---|---|
| `24 REPORT_DPS`, `42 PUB_DPS`, `43 READ_DPS` | Repeated 3-byte DP triplets (§4.2), read until the frame ends |
| `18 SET_WIFI_DATA` | `Byte 2` certificate flag, `Byte 3..` ASCII name |
| `45 TIMER_READ_NEW` | `Byte 2` record count, then that many 7-byte timer records from `Byte 3` |
| `49 CENTRAL_READ` | Remote-slot list (not specified here) |
| `2 ACTION`, `3 SETTING`, `4 READ_SETTING` | Not decoded |

A timer record uses the same layout as the save payload (§4.5):

```
Byte 0     activated = (b0 >> 7) & 1,  t_id = b0 & 0x7F
Byte 1     dp_id
Byte 2..3  value              (big-endian, unsigned 16-bit)
Byte 4..5  minutes            (big-endian); hour = minutes / 60, minute = minutes % 60
Byte 6     weekday mask
```

### 5.3 DP Value Interpretation

A triplet's 16-bit payload is interpreted using the DP's declared schema type:

| Schema type | Interpretation |
|---|---|
| `bool` / `boolean` | `false` when the value is `0`, otherwise `true` |
| everything else (`value`, `enum`, …) | the number itself |

Enumerated DPs therefore travel as a **numeric index**, not as the label seen in a
user interface. The ordered list of labels that the index selects is provisioned per
product together with the DP ID, so a client cannot resolve an enum in either
direction without that list.

Triplets whose DP ID is not present in a client's mapping are skipped; the scan still
advances three bytes at a time.

---|---|
| `24 REPORT_DPS`, `42 PUB_DPS`, `43 READ_DPS` | Repeated 3-byte DP triplets (§4.2) |
| `18 SET_WIFI_DATA` | `Byte 0` certificate flag, `Byte 1..` ASCII name |
| `2 ACTION` | `Byte 0` bit 0 carries the resulting on/off state *(unverified)* |
| `3 SETTING`, `4 READ_SETTING` | `Byte 0` bit 4 carries the on/off state within the §4.3 bitfield *(unverified)* |

Bodies for `45 (TIMER_READ_NEW)` and `49 (CENTRAL_READ)` are not yet specified.

## 6. Physical & Operational Characteristics

1. **Single Connection Slot**: Devices accept only **one simultaneous BLE link**. When disconnected improperly, BlueZ/OS stale connections must be closed and approximately 12 seconds waited before reconnecting.
2. **Notify Before Write**: The client MUST subscribe to notifications before issuing GATT write commands.
3. **Transport Parameters**: An MTU of 256 is requested after connecting. Writes are
   issued without response, and payloads longer than 20 bytes are split into 20-byte
   chunks. Ordinary control frames are 6–10 bytes and fit a single write.
4. **Movement Streaming (`REPORT_DPS`)**: While the window opener motor is running, it streams `REPORT_DPS` (opcode 24) packets with current position `dp0`. Movement completion is detected when streaming ceases for > 3 seconds.
5. **End-stop Position Normalization**: Motors stop mechanically just before reaching theoretical endpoints. Positions $\le 2\%$ should be snapped to $0\%$, and $\ge 98\%$ snapped to $100\%$.
6. **Command Coalescing**: Consecutive commands sent during connection setup or in-flight execution must overwrite pending commands to ensure only the latest intended state is dispatched to the motor.
